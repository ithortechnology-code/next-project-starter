# Auth observability and privacy

## Questions and signals

| Question                                                               | Local signals                                                                                                                  |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Which lifecycle requests succeed, are rejected, or fail operationally? | `starter.auth.operation.count` by bounded operation/outcome; structured `auth.operation` events                                |
| Is auth or email slow?                                                 | `starter.auth.operation.duration` histogram in seconds; use p95/p99, not averages                                              |
| Did a verification/reset message actually send?                        | Email operations report `delivered` after SMTP resolves, or `failure` after rejection; request acceptance alone proves neither |
| Can an individual failure be traced without exposing account data?     | Request IDs, `entryPoint=auth_http`, active trace IDs, and redacted HTTP logs/traces                                           |

Operations cover registration, verification/resend, sign-in/out, recovery/reset, recovery links, session checks, and verification/reset email delivery. Request outcomes use `accepted`, `rejected`, `failure`; session lookup distinguishes `authenticated` and `anonymous`. Successful session polling contributes metrics without per-poll lifecycle info events. A manual SMTP span preserves the request trace through asynchronous delivery and records failure status without exception details. Request IDs are generated by Fastify, returned as `x-request-id`, and propagated through async auth/email work. Startup diagnostics carry a generated ID and explicit startup entry point. Better Auth free-form diagnostic messages/arguments are discarded; handled rejection comes from the request outcome, and library errors emit only a stable event.

These are operational request funnels, not unique-user conversion analytics. Registration and recovery acceptance can intentionally hide whether an account exists. Repeated requests/retries are counted separately. This starter sends no client product-analytics events, assigns no cross-device analytics identity, and makes no claims about abandoned screens. Forks adding client analytics must define consent, retention and allowlisted fields first; never use user IDs, emails, request IDs, raw URLs or error text as metric labels.

## Redaction boundaries

Next.js raw incoming-request logging, full fetch URLs, browser-console forwarding and server-function logs are disabled. The auth proxy catches upstream connection errors, emits a structured `auth.proxy.failed` event with a generated request ID and `web_auth_proxy` entry point, and returns a generic 503 with the matching ID. It never logs the request URL or exception. Native UI code emits no credential-bearing console logs.

Fastify serializers log method and route template rather than raw request URLs; they omit hostnames, IPs, headers, request bodies, error messages and stacks. Query values and reset path tokens are redacted. Credential keys also have Pino redaction rules. Auth event payloads contain only operation/outcome, correlation and entry-point fields. SMTP exceptions and recipient addresses are never passed to the log callbacks.

Before OTLP trace export, an explicit attribute allowlist retains HTTP method/status/route templates, database system/operation names and SDK/service identifiers. It drops URLs, SQL, headers, exception messages, links and events; span status retains only its code. Resource auto-detection is disabled to avoid exporting process arguments and host/user details. This intentionally limits low-level trace detail. Add attributes only with a privacy review and a regression test. Existing endpoint rate/error/duration metrics remain in place.

## Local verification

Run `npm run test:telemetry --workspace=@starter/api`, API email/auth tests, and workspace checks. The telemetry test launches a child process with real SDK/exporters and a local OTLP receiver. It verifies exported trace/metric traffic, correlated structured events, an induced email failure, and absence of sentinel credentials in logs and exports. The auth integration suite exercises real success/rejection, rolling expiry, reset/sign-out revocation and token redaction against isolated PostgreSQL/Mailpit.

See the [runbook](runbooks/auth-failures.md). This local receiver fixture verifies emitted OTLP data; it is not a claim that OpenObserve dashboards, staging traces, alerts, or production delivery have been verified. Those external checks are deferred under the local-only scope.

## Task-by-task review

| Auth tasks                              | Review result                                                                                                                                                                                                                                            |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1–5: specifications and styling         | Static design work needs no operational event stream; scope, platform limits and verification evidence are recorded.                                                                                                                                     |
| 6: email                                | Actual SMTP completion/failure and duration emit bounded events with inherited request context; recipient/link/error details are excluded.                                                                                                               |
| 7–10: API, sessions, migration, origins | Lifecycle request outcomes, valid/anonymous session counters, HTTP RED metrics, safe library diagnostics and expiry/revocation integration tests are in place. Migration/provisioning are explicit local operations; they do not send account analytics. |
| 11: web                                 | Raw request/fetch logging is disabled, upstream proxy errors return generic 503, and browser lifecycle/failure tests verify public feedback.                                                                                                             |
| 12: native                              | UI code does not log credentials or deep links. API instrumentation covers native-origin requests. No new client analytics collector or identity is introduced.                                                                                          |
| 13–14: tests and troubleshooting        | Sentinel export/log tests, real API/email suites, browser/native state tests, and failure/runbook documentation provide regression evidence.                                                                                                             |
| 15–20: optional recipe                  | No-auth generation removes auth-only telemetry and tests while preserving generic HTTP instrumentation and privacy export filtering. Clean recipe verification covers both outputs.                                                                      |

Local OTLP receiver checks include logs, traces, metrics, trace-ID correlation, and a deliberately failed email send. This completes the local instrumentation review; external staging/alert/dashboard verification remains deferred.
